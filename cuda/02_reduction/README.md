# 02 reduction —— divergence、bank conflict、warp shuffle、grid-stride

把 n 个 float 加成 1 个。看起来比向量加还简单，实际上是 **CUDA 里最经典的
优化练习**：从最直白的写法到追平官方库，中间隔着 **5.6 倍**。

难点在于归约是 **"多对一"** 的：GPU 上没有全局同步，一个 block 内部只能
用 `__syncthreads()`，跨 block 只能靠**多趟 kernel**。所以每一版要解决的
问题不只是"怎么算得快"，还有"怎么组织这个多对一的结构"。

理想访存量按 **输入只读一遍** 算（`n × 4` 字节）。中间部分和的读写不计入 ——
那是实现的开销，正是要被优化掉的东西。同样的口径见
`../../triton/02_fused_softmax/_shared.py`。

测试环境：A100-SXM4-40GB（108 SM，40 MB L2，峰值带宽 **1555.2 GB/s**），
CUDA 12.4，`-arch=sm_80`，`CUDA_VISIBLE_DEVICES=7`。

---

## 1. 变体一览

n = 2²⁶（64M float = 256 MB），block = 256：

| 文件 | 修掉的问题 | 耗时 | 带宽 | 占峰值 | 较上一版 |
|------|-----------|------|------|-------|---------|
| `v0_interleaved.cu` | —（教科书第一版） | 1097.7 us | 244.5 GB/s | 15.7% | — |
| `v1_no_divergence.cu` | warp divergence | 672.8 us | 399.0 GB/s | 25.7% | 1.63x |
| `v2_sequential.cu` | shared memory bank conflict | 520.2 us | 516.0 GB/s | 33.2% | 1.29x |
| `v3_first_add.cu` | 一半线程从头闲着 | 279.6 us | 960.2 GB/s | 61.7% | 1.86x |
| `v4_shuffle.cu` | 最后 5 轮的 shared + 同步 | 201.7 us | 1330.7 GB/s | 85.6% | 1.39x |
| `v5_gridstride.cu` | **整体结构**：block 太多、活太碎 | **196.6 us** | **1365.3 GB/s** | **87.8%** | 1.03x |
| `v6_cub.cu` | （官方基线，不是我们写的） | 190.5 us | 1409.4 GB/s | 90.6% | — |

**v0 → v5 总共 5.58x**，最终到 CUB 的 96.9%。

参考点：`../01_vector_add` 里测到流式 kernel 的实际天花板是 ~85%
（`cudaMemcpy` D2D 只有 83.4%）。归约能到 87.8% 是因为它**只读不写**，
没有写带宽的开销 —— 别拿这个数字和向量加的直接比。

> 几个不那么显然的点，都在 §3：
> - v1→v2 修掉 bank conflict 只有 1.29x，而"少开一半 block"有 1.86x ——
>   **结构上的浪费比微观的访存冲突值钱得多**。
> - v4 里 `warpSize` 换成字面量 `32`，白拿 **1.19x**（§3.5）。
> - v5 相比 v4 只快 3%，但**对 block 大小几乎免疫**（§3.3）——
>   这才是它真正的价值。
> - grid-stride 在 `../01_vector_add` 里**一点收益都没有**，这里有（§3.4）。
> - 这张表最早的版本 v0 写的是 12.2%、v0→v1 是 2.09x，**是错的** ——
>   v0 排在第一个被测，替整个进程背了 GPU 时钟爬坡的锅。
>   现在 `bench` 会先 `warmup_gpu()` 空转 200 ms 再计时（§5.6）。

## 2. 使用方法

```bash
make              # 编译出 ./bench
make run          # 全部对比 + 三组扫描（约 30 秒）
make quick        # 只跑正确性 + 变体对比（约 5 秒）
make sass         # 每一版的 LDS/STS/SHFL/BAR 指令统计，见 §3.5
make ptx          # 导出 PTX
make sanitize     # compute-sanitizer memcheck，查越界（~1 秒）
make racecheck    # compute-sanitizer racecheck，查漏掉的 __syncthreads()（~2 秒）
make clean

make GPU=3 run    # 换一张卡
```

> 两个 sanitizer 目标跑的是 `./bench --check`（只跑正确性用例，
> 最大 2²⁰），不是完整 benchmark。sanitizer 下每条访存都要插桩，
> n = 2²⁶ 的 benchmark 要跑几十分钟 —— 而查越界和 race，
> 小用例完全够。

`make racecheck` 是这个练习特有的。**实测验证过它有用**：
把 `v2_sequential.cu:45` 的 `__syncthreads()` 删掉之后 ——

- `n = 256 / 1000 / 1024 / 65537` 四个用例**照样 PASS**，
  答案完全正确；只有 `n = 2²⁰` 才错（相对误差 2.3e-2）。
- racecheck 直接指到行：
  `Write access at reduce_sequential(...) in v2_sequential.cu:43 [131452 hazards]`

这就是归约最阴的地方：**漏一次同步，小尺寸下是对的**
（block 少、warp 内天然同步掩盖了问题），换个尺寸或换张卡才炸。
靠跑几个用例是查不出来的，得靠工具。

> 测性能前先 `nvidia-smi` 看卡是不是空的。
> `bench` 在计时前会先 `warmup_gpu()` 空转 200 ms 把 GPU 时钟拉到稳态 ——
> 不做这一步的话，进程里**第一个**被测的变体会虚慢 20~30%（§5.6）。
> 加了之后实测冷启动和连跑第二遍的数字完全一致，逐字相同。

正确性用例故意包含 `1000`、`65537`、`2²⁰+7` 这些**非 2 的幂、非 block 倍数**
的尺寸 —— 归约的边界处理（补 0）只有这些尺寸才测得出来。
参考值用 `double` 在 CPU 上累加：2²⁶ 个数用 `float` 顺序累加会严重丢精度，
**反而是 GPU 的树形归约更准**，拿 float 参考值会得出错误结论。

## 3. 实测结果

### 3.1 前三版：divergence 和 bank conflict 各值多少

v0 / v1 / v2 做的加法**完全一样**，只是"由哪个线程做"和"数据放在
shared 的哪个槽"不同。三版的 SASS 指令统计也完全一样
（都是 `1 LDG + 3 LDS + 2 STS + 2 BAR`），差别纯粹在**访问模式**上：

| | 谁干活 | 问题 | 带宽 |
|---|--------|------|------|
| v0 | `tid % (2s) == 0` | 每个 warp 半干半闲，32 个 warp 全 divergent | 244.5 GB/s |
| v1 | `index = 2*s*tid` | 干活线程连续了，但访问 shared 的**步长是 2s** → bank conflict | 399.0 GB/s |
| v2 | `tid < s`，前半加后半 | 步长恒为 1，无冲突 | 516.0 GB/s |

- **消除 divergence：1.63x**。v0 里一个 warp 的 32 个 lane 有一半在
  执行空指令，直接浪费一半发射槽。
- **消除 bank conflict：1.29x**。shared memory 有 32 个 bank，
  4 字节一轮转。v1 第 s 轮的访问步长是 2s，s=1 时步长 2 → 2 路冲突，
  s=2 时步长 4 → 4 路，……最坏 32 路。

顺序反过来了才有意思：**divergence 比 bank conflict 贵得多**。
先修哪个不是随便选的。

### 3.2 最大的一步不是微观优化，是少开一半 block（1.86x）

v3 唯一的改动：每个线程 load **两个**元素、读进来就先加一次。

```
v2:  256 线程 读 256 元素 → 树形归约 8 轮 → 262144 个 block
v3:  256 线程 读 512 元素 → 树形归约 8 轮 → 131072 个 block
```

树形归约的第一轮 `s = blockDim/2`，本来就只有一半线程干活。既然如此，
不如让全部线程在 load 阶段就各干一次加法 —— **同样的线程数处理 2 倍数据**。

1.86x，是整条链上最大的单步收益，而且它不属于任何"访存技巧"，
纯粹是**别让线程闲着**。§1 那句"结构上的浪费比微观冲突值钱"就是指这个。

### 3.3 v5 真正买到的是"不用调参"

block 大小 × 变体，n = 2²⁶（单位：占峰值百分比）：

| block | v0 | v1 | v2 | v3 | v4 | **v5** |
|------:|----|----|----|----|----|--------|
| 64   | 20.0% | 21.3% | 21.4% | 42.2% | 42.4% | **74.3%** |
| 128  | 18.0% | 26.3% | 33.9% | 62.4% | 81.0% | **86.4%** |
| 256  | 15.7% | 25.7% | 33.2% | 61.5% | **85.6%** | **87.8%** |
| 512  | 13.4% | 23.7% | 29.0% | 54.2% | 84.3% | **88.3%** |
| 1024 | 10.7% | 19.5% | 23.3% | 43.2% | 78.4% | **88.7%** |

两件事：

1. **v0~v3 越大越慢，v4/v5 不是。** v0 在 block=64 时反而最快（20.0%）——
   因为它的代价是「每个 block 内部要做 log2(blockDim) 轮串行归约，
   且每轮都 divergent」，block 越大这个串行尾巴越长。
   v4 用 shuffle 把尾巴砍了，所以能享受大 block 的好处。

2. **v5 从 64 到 1024 只差 14.4 个点，其中 128~1024 只差 2.3 个点；
   v4 差 43.2 个点。** v5 比 v4 在最优点上只快 3%，但你**随便挑一个
   block 大小它都接近最优**。生产代码里这个性质比峰值数字值钱 ——
   不用为每个 shape 重新调参。

> block=64 时 v5 掉到 74.3% 不是 block 小的锅，是**总线程数不够**：
> grid 固定在 `108 SM × 8 块`，block=64 时总共只有 55296 个线程，
> 访存并行度喂不满。把 blocks_per_sm 调大就补回来了（见 §3.4）。

### 3.4 grid 该开多大：饱和在「每 SM 8 块」

v5 唯一的结构参数是每个 SM 放几个 block。block = 256，n = 2²⁶：

| 每 SM 块数 | grid | 每线程处理元素 | 带宽 | 占峰值 |
|----------:|-----:|--------------:|------|-------|
| 1  | 108  | 2427 | 787.2 GB/s | 50.6% |
| 2  | 216  | 1213 | 1165.1 GB/s | 74.9% |
| 4  | 432  | 606  | 1344.3 GB/s | 86.4% |
| **8** | **864** | **303** | **1365.3 GB/s** | **87.8%** |
| 16 | 1728 | 151  | 1372.5 GB/s | 88.3% |
| 32 | 3456 | 75   | 1372.5 GB/s | 88.3% |
| 64 | 6912 | 37   | 1372.5 GB/s | 88.3% |

**每 SM 8 块（= 2048 线程 = 该 SM 的满占用）之后就是平的。**
代码里默认取 8。再往上没坏处也没好处 —— 说明瓶颈已经完全是显存带宽，
不是并行度。

**⚠️ 和 `../01_vector_add/README.md` §3.4 对照着看：grid-stride 在向量加上
收益是 0，在这里是必需的。** 为什么？

- 向量加：每个线程读 1 个、写 1 个就结束，**没有任何跨迭代复用的状态**。
  grid-stride 只是换了个索引算法，一样的访存量、一样的指令数。
- 归约：每个线程在**寄存器里维护一个累加器**。吃的元素越多，
  "启动 → 归约 → 写部分和"这套固定成本摊得越薄。从每线程 37 个元素
  到 2427 个元素，固定成本从占大头变成可忽略。

**同一个技巧在不同 kernel 上价值完全不同。** 这是"照着优化清单挨个试"
这种做法失效的地方，也是为什么每一条都得自己测。

### 3.5 ⚠️ `warpSize` 不是常量 —— 一个 token 换 1.19x

写 warp 级归约的标准写法：

```cpp
for (int offset = warpSize / 2; offset > 0; offset >>= 1)
    v += __shfl_down_sync(0xffffffffu, v, offset);
```

看着人畜无害，但 **`warpSize` 是运行时特殊寄存器**（SASS 里的 `WARP_SZ`），
不是编译期常量。编译器不知道循环跑几轮，**展不开**。`make sass` 看得很清楚：

| `warp_reduce_sum` 里 offset 的来源 | SASS 里的 SHFL.DOWN 条数 |
|---|---|
| `warpSize / 2` | **2**（就是循环体，两处调用共用） |
| `32 / 2`（字面量） | **10**（两处调用各展开 5 条） |

性能差别（v4，n = 2²⁶，block = 256，热跑）：

| | 耗时 | 带宽 | 占峰值 |
|---|------|------|-------|
| `warpSize` | 239.6 us | 1120.3 GB/s | 72.0% |
| 字面量 `32` | **201.7 us** | **1330.7 GB/s** | **85.6%** |

**1.19x，改一个 token。** 所以两个文件里都写成
`constexpr int WARP = 32;` 并加了 `#pragma unroll`。

顺带一提，这件事把整个练习的结论都改了：没修之前 v4 只有 72%，
"v5 的结构优化带来 1.22x"看起来是条大新闻；修完 v4 到 85.6%，
v5 就只剩 3% 了，真正的价值转移到了 §3.3 的鲁棒性上。
**基线写得不够好，会让后面每一步的收益都虚高。**

`make sass` 里另一处值得看的：只有 v5 有
`LDG.E.128.CONSTANT` —— `.128` 是 `float4` 的 128 位向量化 load，
`.CONSTANT` 是 `__restrict__` 让编译器走只读数据路径。v0~v4 两个都没有。

### 3.6 数据规模：什么时候 v5 能赢 CUB

| n | 大小 | v4 | v5 | CUB |
|---|------|----|----|-----|
| 2¹⁶ | 0.25 MB | 1.8% | 1.8% | 1.8% |
| 2²⁰ | 4 MB | 20.3% | **26.3%** | **26.3%** |
| 2²² | 16 MB | 55.4% | **87.8%** | 81.0% |
| 2²⁴ | 64 MB | 71.4% | 75.2% | **76.6%** |
| 2²⁶ | 256 MB | 85.6% | 87.8% | **90.6%** |

三件事：

1. **2¹⁶ 时三者完全一样（9.2 us）。** 0.25 MB 的数据，kernel 启动
   （~5 us）和两趟的同步开销就是全部，算法差异被完全淹没。
   小数据量下比的不是 kernel，是 launch overhead。
2. **2²⁰ 打平、2²² 时 v5 反超 CUB（87.8% vs 81.0%）。**
   这两档的数据（4 MB / 16 MB）都装得进 40 MB L2，此时
   "少启动几个 block"比"CUB 那套通用调度"更划算 ——
   CUB 为了对所有 n 都稳，在这个区间让出一点。
   n 越大 CUB 越领先，2²⁶ 时拉开 2.8 个点。
3. **2²⁴（64 MB）那一行三者都掉下去了**（v5 87.8% → 75.2%）。
   64 MB 刚好**略大于 40 MB L2** —— 一部分命中 L2、一部分打到 DRAM，
   是最难受的区间。2²² 全在 L2，2²⁶ 纯 DRAM 流式（预取器工作得很好），
   两头反而都比中间好。这是从数据排序推出来的解释，**没有用 ncu 验证过**；
   想确认的话看 `l2_tex_read_hit_rate`（见 §6 练习 4）。

## 4. 一句话总结

> 归约的性能不在"怎么两两相加"，在"**整体结构怎么组织**"。
> 微观优化（divergence、bank conflict、shuffle）连乘 2.92x，
> 结构优化（少开 block、每线程多吃数据）连乘 1.92x，
> 而**最便宜的一步是让编译器能展开循环**（1.19x，改一个 token）。
> 自己写能到官方库的 96.9%（小尺寸上还能反超），
> 但 CUB 在**所有**尺寸上都稳 —— 生产里直接用它。

链条复盘：

```
v0  15.7%  ──消除 divergence──▶       25.7%  (1.63x)  微观
    25.7%  ──消除 bank conflict──▶    33.2%  (1.29x)  微观
    33.2%  ──load 时先加一次──▶       61.7%  (1.86x)  结构  ← 单步最大
    61.7%  ──shuffle + 循环展开──▶    85.6%  (1.39x)  微观 + 编译器
    85.6%  ──grid-stride + float4──▶  87.8%  (1.03x)  结构（买的是鲁棒性）
                                CUB   90.6%
```

## 5. 踩坑记录

1. **`__shfl_down`（无 `_sync`）在 Volta 之后不安全。**
   Volta 引入了独立线程调度（independent thread scheduling），
   warp 内线程**不再保证步调一致**。必须用 `__shfl_down_sync` 并传
   正确的 mask（全 warp 参与就是 `0xffffffff`）。

2. **老教程里 `volatile float* vsmem` 那套写法现在是错的。** 同上原因。
   过去最后 6 轮常写成 `vsmem[tid] += vsmem[tid+32]; vsmem[tid] += ...`
   靠"warp 内天然同步"省掉 `__syncthreads()` —— Volta 之后这个前提没了。
   现在一律用 shuffle 或 cooperative groups。

3. **`warpSize` 不是编译期常量。** 见 §3.5，代价 1.19x。
   同类问题：任何来自特殊寄存器的值（`blockDim.x` 也是）都不能让
   编译器展开循环。要展开就得是模板参数或 `constexpr`。

4. **漏 `__syncthreads()` 常常不报错。** 实测：删掉 v2 的一次同步，
   n ≤ 65537 的四个用例全部 PASS，只有 n = 2²⁰ 才错。
   **写完归约一定跑一次 `make racecheck`**（§2 有完整复现步骤）。

5. **不能用 float 在 CPU 上算参考值。** 2²⁶ 个 [0,1) 的数顺序累加，
   sum 到后面已经是 3×10⁷ 量级，再加 0.5 会被直接吃掉。
   GPU 的树形归约误差是 O(log n)，CPU 顺序累加是 O(n) ——
   **GPU 更准**，拿 CPU float 当参考会误判成"GPU 算错了"。
   用 `double` 累加。

6. **`bench()` 里的 warmup 不等于「GPU 热了」。** 这个坑吃得最狠：
   `bench()` 每次测量前空跑 10 遍，足够热掉 module 载入和 cache，
   但**拉不动 GPU 的时钟**。结果是进程里**第一个**被测的变体
   虚慢 20~30%，后面的都正常 —— 换句话说，对比表的第一行系统性偏慢，
   而第一行恰好是"未优化版本"。这张表最初写的 v0 = 12.2%、
   v0→v1 = 2.09x 就是这么来的，真实值是 15.7% 和 1.63x，
   **第一步的收益被夸大了 28%**。

   修法在 `../common.cuh` 的 `warmup_gpu()`：计时前先用访存密集的
   kernel 空转 200 ms。加完之后冷启动和连跑第二遍的输出逐字相同。

   诊断这个问题的线索：v5/v6 冷热完全一样，只有 v0~v4 变。
   **被显存带宽卡死的 kernel 不受 SM 时钟影响** ——
   反过来，如果一个 kernel 的耗时随时钟变，说明它还不是带宽瓶颈。

7. **基线不够好会让后面每一步都虚高。** §3.5 那个 token 改完之后，
   v5 的收益从 1.22x 缩到 1.03x。写对比实验时，
   **上一版必须是"这个思路能做到的最好"，不是"我第一次写出来的样子"**。

## 6. 练习

1. 把 v4 的 `constexpr int WARP = 32` 改回 `warpSize`，`make sass` 看
   SHFL 条数从 10 变回 2，再 `make run` 复现 §3.5 的 1.19x。
2. 用 `cooperative_groups` 的 `cg::reduce` 重写 v4，看能不能干掉
   最后那次 `__syncthreads()`。
3. 把 v5 改成求 max 而不是 sum（注意：单位元不是 0，是 `-INFINITY`），
   然后和 `cub::DeviceReduce::Max` 比。
4. 用 ncu 验证 §3.6 的 L2 假设：
   ```bash
   /usr/local/cuda/bin/ncu --metrics \
     lts__t_sector_hit_rate.pct,dram__bytes_read.sum \
     --kernel-name reduce_gridstride ./bench --quick
   ```
   看 2²², 2²⁴, 2²⁶ 三档的 L2 命中率是不是中间那档最差。
5. 归约的数值精度：v0~v5 的加法顺序都不同，把结果和 `double` 参考值比，
   看哪一版误差最小。（提示：树形归约的误差是 O(log n)，
   grid-stride 在寄存器里线性累加的那一段是 O(n/线程数)。）

## 7. 和 Triton 版的对照

`../../triton/02_fused_softmax/` 里的 softmax 也要做归约（求 max 和 sum），
但 Triton 里只写一行 `tl.max(x, axis=0)` / `tl.sum(x, axis=0)`。

这整个练习的 v0~v5 —— divergence、bank conflict、shuffle、
grid-stride —— **全部是 Triton 编译器替你做的**。这是 Triton 最大的价值：
block 内的归约策略你完全不用管。

反过来，Triton 里你管不了的东西这里能管：grid 开多大、
每个线程吃多少元素、要不要 `float4`。`../../triton/02_fused_softmax/README.md`
里 v2_persistent 那一版就是在 Triton 层面手工模拟 §3.4 的 grid-stride，
能做，但绕。

一句话：**block 内的归约用 Triton，block 间的结构自己想** ——
两边都是这个分工。
