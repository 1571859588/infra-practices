# 03 matmul —— 算术强度、两层分块、寄存器复用

`C = A × B`，全部 row-major、fp32。这是 CUDA 优化里最值钱的一个练习：
从教科书第一版到 cuBLAS 的 88%，中间隔着 **6.7 倍**，而且每一步的
理由都能用一个数算出来。

和前两个练习最大的区别：**01 和 02 都是 memory-bound，这个不是。**
matmul 的优化主线只有一句话 ——

> **把算术强度（每读 1 字节能做多少次浮点运算）提上去，
> 直到越过 roofline 拐点，然后开始抠指令数。**

A100 的拐点：`19.5 TFLOP/s ÷ 1555 GB/s ≈ **12.5 FLOP/byte**`。
低于它是 memory-bound，高于它才轮得到算力说话。

测试环境：A100-SXM4-40GB（108 SM，40 MB L2，fp32 峰值 **19.5 TFLOP/s**，
带宽 1555.2 GB/s），CUDA 12.4，`-arch=sm_80`，`CUDA_VISIBLE_DEVICES=7`。

---

## 1. 变体一览

M = N = K = 4096（137.4 GFLOP）：

| 文件 | 核心手段 | 算术强度 | 耗时 | 算力 | 占峰值 | 较上一版 |
|------|---------|---------|------|------|-------|---------|
| `v0_naive.cu` | —（一线程一输出） | 0.25 | 56757 us | 2.42 TFLOP/s | 12.4% | — |
| `v1_smem.cu` | shared memory 分块 32×32 | 8 | 25911 us | 5.30 TFLOP/s | 27.2% | 2.19x |
| `v2_regtile.cu` | **寄存器分块** 64×64，一线程 4×8 | 16 | 12818 us | 10.72 TFLOP/s | 55.0% | 2.02x |
| `v3_vec4.cu` | float4 + 128×128，一线程 8×8 | 32 | **8433 us** | **16.30 TFLOP/s** | **83.6%** | 1.52x |
| `v4_cublas.cu` | （官方基线，不是我们写的） | — | 7459 us | 18.43 TFLOP/s | 94.5% | — |

**v0 → v3 总共 6.7x**，最终到 cuBLAS 的 **88.5%**。

> cuBLAS 这一档在多次运行间有 ±1% 的抖动（7459~7538 us，18.23~18.43
> TFLOP/s），所以"88.5%"实际是 88~89%。自己写的三版重复性很好，
> 连跑三遍最大偏差 0.1%。

> 几个不那么显然的点，都在 §3：
> - **占用率（occupancy）和性能在这里是反着的**：v0/v1 是 100%，
>   v2/v3 只有 25% —— 而快的是后者（§3.4）。这和 01/02 的结论相反。
> - v1 的瓶颈**已经不是显存带宽了**，是 shared memory 带宽。
>   算术强度 8 的理论上限是 12.4 TFLOP/s，实测只有 5.30（§3.1）。
> - v2 → v3 两版的 FFMA 条数**完全一样**（都是 513 条），
>   差别全在访存指令条数上（§3.2）。
> - 小矩阵上分块越大越慢：256³ 时 v3 比 v1 慢 **4 倍**（§3.3）。
> - K 少 1 个元素，性能掉 **1.53x**（§3.5）。
> - cuBLAS 默认可能偷偷用 TF32，快 6.7x 但那不是 fp32（§3.6）。

## 2. 使用方法

```bash
make              # 编译出 ./bench（链接 -lcublas）
make run          # 全部对比 + 两组扫描（约 4 分钟，v0 在 4096³ 上要 57 ms/次）
make quick        # 正确性 + 占用率 + 变体对比（约 1.5 分钟）
make sass         # 每一版的 FFMA / LDS / LDG / STG 指令统计，见 §3.2
make regs         # 每一版的寄存器和 shared memory 用量，见 §3.4
make ptx          # 导出 PTX
make sanitize     # compute-sanitizer memcheck，查越界（~40 秒）
make racecheck    # compute-sanitizer racecheck，查漏掉的 __syncthreads()
make clean

make GPU=3 run            # 换一张卡
MATMUL_TF32=1 ./bench --quick   # 让 cuBLAS 走 TF32 Tensor Core，见 §3.6
```

两个 sanitizer 目标跑的是 `./bench --check`（只跑正确性用例，最大
1000³），不是完整 benchmark —— 理由和 `../02_reduction` 一样：
sanitizer 下每条访存都要插桩，4096³ 要跑几十分钟。
实测结果：**memcheck 0 errors，racecheck 0 hazards**。

### 正确性用例和容差

`bench.cu` 的 `CASES` 故意包含这些形状：

| 用例 | 测什么 |
|------|-------|
| `128³` / `256×512×128` | 所有分块大小的整数倍 → 走全部快路径 |
| `129×257×65` | 三个维度谁都不整除 → 边界补 0 的逻辑 |
| `1×4096×4096` / `4096×1×4096` | 退化成矩阵向量乘 → 暴露 grid 算成 0 |
| `100×100×3` | K 极小，k 循环只跑一轮 |
| `512×512×511` / `1000³` | 常见的"差一点"尺寸 |

两个容易忽略的细节：

1. **容差必须跟着 K 走。** fp32 累加 K 次，随机符号下误差按 `sqrt(K)`
   量级增长。固定 `1e-5` 在 K=4096 时必然误报，所以用的是
   `tol = 1e-5 * sqrt(K) * 4`。
2. **每次跑之前把 C 填成 NaN**（`cudaMemset(dC, 0x7F, ...)`）。
   如果 grid 算错导致 kernel 根本没覆盖某些位置，填 0 的话结果
   可能"恰好接近对"，填 NaN 就一定会被 `check` 抓到。

参考值用 **CPU double 累加**。输入取 `[-1, 1]` 而不是 `[0, 1)`：
全正数累加会让误差单调增长，反而掩盖真正的 bug（符号错、索引错
都可能还"差不多对"）。

> **测性能前先确认卡是空的。** 本页所有数字都是在空闲卡上测的。
> 同一份代码在被占的卡上实测：cuBLAS 从 18.43 掉到 8.68 TFLOP/s，
> v3 从 16.30 掉到 7.06 —— 但 v0→v3 的比值从 6.7x 只变到 6.9x，
> **比值稳，绝对值不稳**。自查办法见 `../README.md` §3.3
> （`nvidia-smi` 可能跑不起来，那边给了 NVML 的替代命令）。
>
> 另外 `bench` 在计时前会 `warmup_gpu()` 空转 200 ms 把 GPU 时钟拉到稳态 ——
> 不做这一步，进程里第一个被测的变体会虚慢 20~30%。
> 这个坑是在 `../02_reduction` 里踩到的，见那边的 §5.6。

## 3. 实测结果

### 3.1 主线：算术强度，以及它什么时候不再是瓶颈

算术强度的推导（只算 global → shared 那一层）：

```
一个 BM×BN 的输出块，每个 k-tile 要搬 (BM×BK + BK×BN) 个 float，
用它们做 BM×BN×BK×2 次浮点运算。

强度 = 2·BM·BN·BK / (4·BK·(BM+BN)) = BM·BN / (2·(BM+BN))
```

| 变体 | 分块 | 算术强度 | 相对拐点 12.5 | 理论上限* | 实测 |
|------|------|---------|--------------|----------|------|
| v0 | 无 | 0.25 | 2% | 0.39 TFLOP/s | **2.42** ← 比上限还高？ |
| v1 | 32×32 | 8 | 64% | 12.4 TFLOP/s | 5.30 ← 差一半 |
| v2 | 64×64 | 16 | 128% | 19.5（封顶） | 10.72 |
| v3 | 128×128 | 32 | 256% | 19.5（封顶） | 16.30 |

\* 理论上限 = min(强度 × 1555 GB/s, 19.5 TFLOP/s)

**这张表上下两处"对不上"，才是真正要理解的东西：**

**① v0 比模型预测的快 6.2 倍。**
因为 0.25 这个数假设了"每次都从 DRAM 读"，而实际上 **L1/L2 兜住了大部分
复用** —— A100 有 40 MB L2，4096×4096 的一行 A（16 KB）读进来之后
会被后续大量线程命中。反推 v0 的**有效**算术强度是
`2.42e12 / 1555e9 ≈ 1.56 FLOP/byte`，比纸面的 0.25 高 6 倍多。

> 教训：算术强度的纸面值是**下界**，不是预测值。cache 会替你复用一部分，
> 但你控制不了它复用多少 —— 这正是要显式用 shared memory 的理由。

**② v1 只有模型预测的 43%。**
这说明 v1 **已经不是显存带宽受限了**，瓶颈换人了 —— 换成了
**shared memory 带宽**。

估算一下：v1 每做一次 FFMA 要从 shared 读 2 个 float = 8 字节，
也就是 **4 字节/FLOP**。A100 的 shared memory 吞吐约
`32 banks × 4 B × 1.41 GHz × 108 SM ≈ 19.5 TB/s`，于是

```
19.5e12 B/s ÷ 4 B/FLOP ≈ 4.9 TFLOP/s     （实测 5.30）
```

同一量级，方向对得上。（这是个粗估 —— 峰值 clock、LSU 发射率都有
出入，别把它当精确预测，它的作用是**指认瓶颈在哪一级存储**。）

`make sass` 的数字直接印证：v1 是 **33 条 FFMA 配 40 条 shared 读**，
几乎一比一。每一次乘加都要去 shared 取两个数，当然跑不动。

**v2 的寄存器分块，修的就是这个。** 一个线程算 TM×TN 个输出，
每个 k 只读 TM+TN 个数到寄存器，却能做 TM×TN 次 FFMA：

```
v1:  2 次 shared 读  →   1 次 FFMA      比值 0.5
v2: 12 次 shared 读  →  32 次 FFMA      比值 2.67   (TM=4, TN=8)
v3: 16 次 shared 读  →  64 次 FFMA      比值 4.0    (TM=8, TN=8)
```

这才是 "两层分块" 的真正含义 —— 第二层复用发生在**寄存器**里：

```
global memory ──BM×BK 块──▶ shared memory ──TM×TN 块──▶ 寄存器
     慢、大                    中、每 block 共享          快、每线程私有
```

cuBLAS / CUTLASS 也是这个结构，只是多了 double buffering、
更精细的 swizzle，以及 Tensor Core。

### 3.2 v2 → v3：FFMA 一条没变，快了 1.52x

`make sass` 的输出（每个 kernel 的静态指令统计）：

| | FFMA | shared 读 | shared 写 | global 读 | global 写 |
|---|---|---|---|---|---|
| v0 | 30 | — | — | 58 `LDG.E.CONSTANT` + 1 `LDG.E` | 2 `STG.E` |
| v1 | 33 | 32 `LDS` + 8 `LDS.128` | 2 `STS` | 2 `LDG.E.CONSTANT` + 1 `LDG.E` | 2 `STG.E` |
| v2 | **513** | 48 `LDS.128` | 16 `STS` | 16 `LDG.E.CONSTANT` + 1 `LDG.E` | 33 `STG.E` |
| v3 | **513** | **32 `LDS.128`** | 4 `STS` + 1 `STS.128` | **2 `LDG.E.128.CONSTANT`** + 1 `LDG.E` | **16 `STG.E.128`** + 1 `STG.E` |

（`.CONSTANT` 是编译器给 `const __restrict__` 指针加的只读缓存提示，
走 `__ldg` 那条路径；每一版都有的那 1 条零散 `LDG.E` 来自边界/参数加载，
不在主循环里。）

v2 和 v3 的 **FFMA 条数完全相同（513 条）** —— 干的活一模一样。
差别全在访存指令上：

- shared 读：48 → 32 条（−33%），来自 TM×TN 从 4×8 变 8×8
- global 读：17 条标量 → **2 条 `LDG.E.128`**（float4，一条顶四条）
- global 写：33 条标量 → **16 条 `STG.E.128`**

**1.52x 完全来自"少发指令"，不是"少搬数据"。** 算术强度 16 → 32
这件事在这里其实没起作用 —— 都已经在拐点右边了，访存量早就不是瓶颈。

> 一个反直觉的发现：**v2 里的 shared 读，编译器自己就向量化成
> `LDS.128` 了**（源码写的是普通的 `a_reg[i] = As[k][...]` 标量循环）。
> 所以 v3 在 shared→寄存器上显式写 `float4` 并没有额外收益，
> 真正新增的是 **global→shared 的 `LDG.E.128`** 和更大的分块。
> 这也说明：加 `float4` 之前，先 `make sass` 看看编译器是不是已经做了。

### 3.3 小矩阵上，分块越大越慢

`make run` 的规模扫描（单位 TFLOP/s，越大越好）：

| 规模 | v1 (32×32) | v2 (64×64) | v3 (128×128) | cuBLAS |
|------|-----------|-----------|-------------|--------|
| 256³ | **1.82** | 0.96 | 0.46 | 2.05 |
| 512³ | 3.69 | **4.30** | 1.93 | 8.46 |
| 1024³ | 5.03 | 7.80 | **8.04** | 16.01 |
| 2048³ | 5.39 | 10.02 | **12.43** | 17.59 |
| 4096³ | 5.30 | 10.72 | **16.28** | 18.23 |

**256³ 上 v3 比 v1 慢 4 倍，比自己在 4096³ 上的水平低 35 倍。**

原因是并行度，用 block 数一算就清楚了。block 数 = `(S/BM)²`，
而每个 SM 能同时驻留的 block 数见 §3.4：

| 规模 | v1 块数 / 需要 216 | v2 块数 / 需要 432 | v3 块数 / 需要 216 |
|------|------------------|------------------|------------------|
| 256³ | 64（30%） | 16（4%） | **4（2%）** |
| 512³ | 256（✓ 满） | 64（15%） | 16（7%） |
| 1024³ | 1024（✓） | 256（59%） | 64（30%） |
| 2048³ | 4096（✓） | 1024（✓） | 256（✓ 满） |

256³ 时 v3 只开出 **4 个 block**，而卡上有 **108 个 SM** —— 
96% 的 GPU 在发呆。分块大 = 算术强度高 = 单块效率高，但同时
**块数少 = 填不满 GPU**。两者是直接冲突的。

v3 要到 **2048³ 才填得满**，这也正好是它开始明显领先 v2 的点。

> cuBLAS 在 256³ 上仍有 2.05 TFLOP/s，比我们三版都快 —— 它换了 kernel。
> 这就是"真实的库为什么要维护几十个 shape 专用 kernel + 一套启发式
> 选择逻辑"的答案。**不存在一个在所有尺寸上都最优的分块。**

### 3.4 ⚠️ 占用率越低反而越快

`./bench` 会先打印一张静态资源表（CUDA Occupancy API 算的，
**不需要 root** —— 和 `ncu` 读性能计数器不一样）：

```
variant            thr/blk   regs  smem/blk  blk/SM occupancy
v0_naive               256     32       0 B       8    100.0%
v1_smem               1024     32    8192 B       2    100.0%
v2_regtile             128    122    8192 B       4     25.0%
v3_vec4                256    123    8192 B       2     25.0%
```

和性能并排放：

| | occupancy | 实测 |
|---|---|---|
| v0 | 100.0% | 2.42 TFLOP/s |
| v1 | 100.0% | 5.30 TFLOP/s |
| v2 | 25.0% | 10.72 TFLOP/s |
| v3 | 25.0% | **16.30 TFLOP/s** |

**完全反向相关。** 这和 `../01_vector_add`、`../02_reduction` 的结论
正好相反 —— 那两个练习里，占用率不够就藏不住访存延迟。

区别在于**靠什么隐藏延迟**：

- **memory-bound kernel 靠 TLP**（thread-level parallelism）：
  一个 warp 卡在等 DRAM，就切到另一个 warp。warp 不够多就只能干等，
  所以要高 occupancy。
- **compute-bound kernel 靠 ILP**（instruction-level parallelism）：
  v3 的每个线程手里握着 **64 个互相独立的 FFMA**（`acc[8][8]`），
  流水线自己就填满了，根本不需要别的 warp 来救场。

而这 64 个累加器只能放在寄存器里 —— 于是 123 个寄存器/线程，
按 8 对齐到 128，×256 线程 = 32768，SM 一共 65536 个，
**每 SM 只放得下 2 个 block**。占用率 25% 是**换来 ILP 付的价钱，
而且这笔买卖很划算**。

> 所以 "occupancy 要拉满" 是个有前提的建议。先判断 kernel 是
> memory-bound 还是 compute-bound，再决定要不要为它牺牲寄存器。
> `make regs` 可以直接看每一版的寄存器用量。
>
> 注意 shared memory 从头到尾都不是瓶颈：四版里用得最多的也只有
> 8 KB/block，×2 block = 16 KB，离 A100 的 164 KB/SM 远得很。

### 3.5 差一个元素，慢 1.53x

v3 的 kernel 内部**没有任何边界判断** —— 这是它快的一部分原因。
代价是它只在尺寸整除时能用，否则 `matmul_v3_vec4()` 会退回 v2：

```cpp
bool fast_path_ok(int M, int N, int K) {
    return M % BM == 0 && N % BN == 0 && K % BK == 0 && N % 4 == 0 && K % 4 == 0;
}
```

实测这条分界线的代价：

| 形状 | 路径 | 算力 | 占峰值 |
|------|------|------|-------|
| 4096×4096×**4096** | 快路径 | 16.30 TFLOP/s | 83.6% |
| 4096×4096×**4088** | 快路径（K 少 8，仍整除） | 16.55 TFLOP/s | 84.9% |
| 4096×4096×**4095** | **退化到 v2** | 10.68 TFLOP/s | 54.8% |
| **4095**×4096×4096 | **退化到 v2** | 10.72 TFLOP/s | 55.0% |

**K 从 4096 变成 4095，少算 0.02% 的活，慢了 1.53 倍。**

（K=4088 那档比 K=4096 还快 1.5%，是因为少了一个 k-tile 加上运行间
抖动，不是什么真实效应 —— 别过度解读。）

这正是生产代码里 padding 到 128 倍数如此常见的原因，也再次说明
§3.3 的那句话：**库不是靠一个万能 kernel 快的，是靠一堆专用 kernel
加一个挑选器。** 我们这里的 `fast_path_ok` 就是那个挑选器的最简版本。

### 3.6 ⚠️ cuBLAS 的 fp32 可能根本不是 fp32

A100 的 Tensor Core 支持 **TF32**：19 bit 格式，8 bit 指数（和 fp32 一样）
但尾数只有 **10 bit**（fp32 是 23 bit）。峰值 156 TFLOP/s，是 fp32
CUDA core 的 8 倍。**`cublasSgemm` 在某些 CUDA 版本 / 环境变量下会
默认走它** —— 接口没变、类型没变，精度悄悄掉三个数量级。

所以 `v4_cublas.cu` 里显式写死了：

```cpp
cublasSetMathMode(g_handle, CUBLAS_PEDANTIC_MATH);   // 强制真 fp32
```

打开开关对比（`MATMUL_TF32=1 ./bench --quick`）：

| cuBLAS 模式 | 4096³ 耗时 | 算力 | 1000³ 上的 max_abs_err | 正确性用例 |
|------------|-----------|------|----------------------|-----------|
| `PEDANTIC_MATH`（真 fp32） | 7538 us | 18.23 TFLOP/s | 1.81e-05 | 全部 PASS |
| `TF32_TENSOR_OP_MATH` | **1125 us** | **122.13 TFLOP/s** | **1.45e-02** | **5/8 FAIL** |

**快 6.7 倍，误差大 800 倍。**

有两个信号可以在不知情的时候发现这件事：

1. 打印里出现了 `(626.3% of peak)` —— **占峰值超过 100% 就说明
   你比的不是同一个峰值**。这是个免费的自检，值得在所有 benchmark
   里都留着。
2. 正确性用例直接判 FAIL（128³ 上 2931/16384 个元素超差）。
   如果当初把容差设得很松，或者干脆不测正确性，就会得出
   "我的 kernel 只有 cuBLAS 的 13%" 这种既真实又完全误导的结论。

> 不是说 TF32 不能用 —— 深度学习里它是默认选择，精度足够。
> 问题只在于**拿它当 fp32 kernel 的对比基线是不公平的**，
> 那不是同一种运算。

## 4. 一句话总结

> matmul 的性能不在"循环怎么写"，在"**数据在存储层次里被复用几次**"。
> 每往上抬一层（DRAM → shared → 寄存器），算术强度翻一倍，
> 直到越过 roofline 拐点 12.5；过了拐点，剩下的活是**减少指令条数**。
> 自己写四版能到 cuBLAS 的 88.5%，
> 但小矩阵上会输 4 倍，非整除尺寸上会输 1.53 倍 ——
> **库的价值不在单个 kernel 快，在于它对所有 shape 都不慢。**

链条复盘：

```
v0  12.4%  ──shared 分块，强度 0.25→8──▶   27.2%  (2.19x)  越过 DRAM 瓶颈
    27.2%  ──寄存器分块，强度 8→16──▶      55.0%  (2.02x)  越过 shared 瓶颈 ← 单步最大
    55.0%  ──float4 + 128×128 分块──▶      83.6%  (1.52x)  减少指令条数
                               cuBLAS      94.5%
```

三步各自解决的是**不同一级**的瓶颈，这就是为什么它们能连乘：

| 步骤 | 拆掉的瓶颈 |
|------|-----------|
| v0 → v1 | DRAM 带宽 |
| v1 → v2 | shared memory 带宽 |
| v2 → v3 | 指令发射（instruction issue） |

## 5. 踩坑记录

1. **cuBLAS 是 column-major。** row-major 的 `C = A×B` 要写成
   `cublasSgemm(h, N, N, **N, M, K**, &a, **B, N, A, K**, &b, C, N)` ——
   交换 A/B，M/N 对调。推导见 `v4_cublas.cu` 文件头。
   记不住就记结论，写错了不会报错，只会算出转置的结果。

2. **cuBLAS 的 `Sgemm` 不保证是 fp32。** 见 §3.6，`CUBLAS_PEDANTIC_MATH`。

3. **kernel 里不能在 `__syncthreads()` 之前提前 `return`。**
   分块 matmul 必然遇到"这个线程负责的位置越界了"的情况，
   直觉是 `if (out_of_range) return;` —— **这会死锁**，因为
   `__syncthreads()` 要求 block 内所有线程都到齐。
   正确做法是照常参与同步，只把搬进来的值**补 0**：
   ```cpp
   As[c][r] = (gr < M && gc < K) ? A[gr * K + gc] : 0.0f;
   ```
   补 0 之所以安全，是因为 0 对乘加是零元，不影响结果。

4. **shared memory 里的 A 要转置存。** 计算阶段读的是 A 的**一列**
   （固定 k，连续的 TM 行）。存成 `As[row][k]` 的话沿 row 走步长是
   BK=16 个 float = 64 字节 → 全落进同一个 bank → **16 路 bank
   conflict**。存成 `As[k][row]` 步长就是 1，无冲突。
   代价是搬运时要拆成 4 次标量写（没法向量化），很划算。

5. **`float4` 要求 16 字节对齐。** `cudaMalloc` 保证基址 256 字节对齐，
   但**行首地址**是 `base + row * K * 4` —— K 不是 4 的倍数时就歪了。
   所以 `fast_path_ok()` 里除了检查分块整除，还要单独检查 `K % 4` 和
   `N % 4`。漏掉这条会得到 `misaligned address` 错误，
   而且只在特定尺寸下才炸。

6. **匿名 namespace 里的 kernel 拿不到符号名。**
   `make sass` 和 Occupancy API 都要能引用 kernel。v3 的 kernel 在
   匿名 namespace 里，所以 `occ_v3_vec4()` 必须写在**同一个 .cu 内部**
   （见 `variants.cuh` 里 `make_occ` 模板的注释）。
   `cuobjdump` 里它显示成 `_ZN43_GLOBAL__N__...11matmul_vec4E...` 这种名字。

7. **正确性容差不能是常数。** 见 §2。K=4096 时 fp32 累加的固有误差
   就有 1e-4 量级，用 1e-5 会把正确的 kernel 判成错的，
   然后你会花一小时去 debug 一个不存在的 bug。

8. **`ncu` 在这台机器上需要特权**（`ERR_NVGPUCTRPERM`）。
   Docker 方案见 `../../综合练习/vector_mul2/README.md` §5。
   但**占用率不需要 ncu** —— `cudaOccupancyMaxActiveBlocksPerMultiprocessor`
   是纯静态计算，随便谁都能调，`./bench` 已经内置了（§3.4）。

## 6. 练习

1. 把 v2 的 `TM×TN` 从 `4×8` 改成 `8×8`（BM=BN=64 不变，线程数变成 64），
   看算术强度不变的情况下性能怎么动 —— 验证 §3.2 的
   "shared 读/FFMA 比值" 才是关键。
2. 给 v3 加 **double buffering**：在算当前 k-tile 的同时预取下一个，
   用两组 shared buffer 交替。这是 v3 → cuBLAS 那 11.5% 的主要来源之一。
3. 把 §3.3 的表补完：给 v3 加一个 `BM=BN=64` 的版本，
   验证"小矩阵该用小分块"，并写一个简单的启发式选择器
   （比如按 `M*N/(BM*BN) >= 2*SM数` 来挑）。
4. 用 `__launch_bounds__` 给 v2 限制寄存器（比如 `(128, 4)` 要求
   每 SM 至少 4 个 block），用 `make regs` 看寄存器降到多少，
   再看性能是涨还是跌 —— 这是 §3.4 那个权衡的直接实验。
5. 打开 TF32（§3.6），把我们的 v3 和 TF32 的 cuBLAS 都跑一遍，
   计算各自**相对自己那个峰值**（19.5 / 156 TFLOP/s）的占比，
   看看谁的"效率"更高。
6. 用 ncu（需要 Docker，见 `../../综合练习/vector_mul2/README.md` §5）
   验证 §3.1 的 shared memory 瓶颈假设：
   ```bash
   /usr/local/cuda/bin/ncu --metrics \
     l1tex__data_pipe_lsu_wavefronts_mem_shared.avg.pct_of_peak_sustained_active \
     --kernel-name matmul_smem ./bench --quick
   ```
   v1 上这个数应该接近 100%，v3 上应该低得多。

## 7. 和 Triton 版的对照

`../../triton/03_matmul/` 解的是同一个问题。对照着看最能体会分工：

| | Triton | CUDA（这里） |
|---|---|---|
| 分块大小 | `BLOCK_M/N/K` 是 `tl.constexpr`，`@triton.autotune` 自动扫 | 手写 `constexpr`，自己扫（§3.3） |
| 寄存器分块 | **不用写** —— `tl.dot` 内部就是 | v2 的全部内容 |
| shared memory | **不用写** —— 编译器自动分配和同步 | 手写 `__shared__` + `__syncthreads()` |
| bank conflict | 编译器处理 swizzle | 手动转置 `As[k][row]`（踩坑 4） |
| float4 向量化 | 编译器决定 | 手写 `reinterpret_cast<float4*>`（v3） |
| 边界处理 | `tl.load(..., mask=..., other=0.0)` 一行 | 每处搬运都要写三元表达式（踩坑 3） |
| Tensor Core | `tl.dot` 自动用 | 得手写 `mma` PTX 或用 CUTLASS |

**Triton 用 `tl.dot` 一行就拿到了这里 v2 + v3 的全部工作量**，
而且自动用上 Tensor Core。

⚠️ **两边的绝对数字不能直接比。** Triton 那个练习是
**fp16 输入 / fp32 累加**，峰值按 fp16 dense Tensor Core 的
**312 TFLOP/s** 算；这里是纯 **fp32 CUDA core，峰值 19.5 TFLOP/s**。

| | 数据类型 | 峰值 | 最好成绩 | 占峰值 | 占 cuBLAS |
|---|---|---|---|---|---|
| `triton/03_matmul` v2 | fp16 in / fp32 acc | 312 TFLOP/s | 186.8 TFLOP/s | 60% | 91% |
| 这里 v3 | fp32 | 19.5 TFLOP/s | 16.30 TFLOP/s | 84% | 88.5% |

**看"占峰值"和"占 cuBLAS"才是可比的**，看绝对 TFLOP/s 只会得出
"Triton 快 11 倍"这种毫无意义的结论 —— 那 11 倍是 Tensor Core 和
fp16 带来的，不是编译器带来的。这就是 §3.6 那个教训的另一个版本：
**先确认两边算的是不是同一种运算。**

那这个练习白做了吗？不是 ——

- `@triton.autotune` 扫的那些 `BLOCK_M/N/K/num_warps`，
  **为什么是这些候选值**、**为什么小矩阵要小分块**，答案在 §3.3 和 §3.4。
  不理解的话 autotune 就是黑盒撞运气。
- Triton 也有"非整除尺寸变慢"的现象，原因和 §3.5 完全一样。
- `tl.dot` 之外的部分（epilogue、fusion）还是要自己想数据复用。

一句话：**Triton 替你写 kernel，但不替你想 roofline。**
