# 01 vector_add —— 合并访存、向量化、grid-stride

`out = x + y`，float32。最简单的 memory-bound kernel：每个元素只做 1 次加法，
却要搬 12 字节。算术强度 1/12 FLOP/byte，**性能完全由显存带宽决定**，
和算力一点关系都没有。

这是 `../../triton/01_vector_add/` 的 CUDA 对照版。同一个问题、同样的实验，
看 CUDA 里要自己写什么、Triton 替你做了什么。

测试环境：A100-SXM4-40GB（108 SM，40 MB L2，峰值带宽 **1555.2 GB/s**），
CUDA 12.4，`-arch=sm_80`，`CUDA_VISIBLE_DEVICES=7`。

---

## 1. 变体一览

| 文件 | 做了什么 | 实测（n=2²⁴） | 占峰值 |
|------|---------|--------------|-------|
| `v0_naive.cu` | 一线程一元素，合并访存 | **1319.5 GB/s** | **84.8%** |
| `v1_vec4.cu` | `float4` 向量化，一线程 4 元素 | 1302.0 GB/s | 83.7% |
| `v2_grid_stride.cu` | grid-stride loop，grid 跟硬件走 | 1293.5 GB/s | 83.2% |
| `v3_strided_bad.cu` | **反面教材**：破坏合并访存 | 201.0 GB/s | 12.9% |

参考点：`cudaMemcpy` D2D 是 1297.7 GB/s（83.4%）。
**~85% 就是这台机器上流式 kernel 的实际天花板**，不是 100% ——
refresh、ECC、行切换这些开销是拿不回来的。

> 第一个结论就有点反直觉：**在 block=256 这种常规配置下，
> v0 / v1 / v2 三者的差距在 ±1% 以内，就是噪声。**
> 表里 v0 甚至比 v1 快了 1.3% —— 换一次运行顺序就可能反过来，
> 不要把这种差距当成结论。向量化真正的价值在别的地方，见 §3.1 和 §3.2。

## 2. 使用方法

```bash
make              # 编译出 ./bench
make run          # 编译并运行全部对比 + 扫描（约 40 秒）
make quick        # 只跑正确性 + 变体对比
make ptx          # 导出 PTX，看编译器发了什么访存指令
make sass         # 导出 SASS，看真正执行的机器码
make sanitize     # compute-sanitizer 查越界（会慢 ~30 倍，正常）
make clean

make GPU=3 run    # 换一张卡
make ARCH=sm_90   # 换一种架构（H100）
```

编译器和运行 GPU 的默认值在 `../common.mk` 里，
不必改文件，命令行覆盖就行。工具链的完整说明见 `../../README.md`。

> 测性能前先 `nvidia-smi` 看一眼卡是不是空的。
> 这台机器 GPU 0~6 常被占，7 一般空闲，所以 `common.mk` 里默认 `GPU=7`。
> 在被别人抢着跑的卡上测出来的数字没有任何意义。

## 3. 实测结果

### 3.1 block 大小：v0 敏感，v1 不敏感

```
              v0 朴素              v1 float4
block=32      509.3 GB/s (32.8%)   1319.5 GB/s (84.8%)    ← 2.6x 差距
block=64     1008.2 GB/s (64.8%)   1302.0 GB/s (83.7%)    ← 1.3x 差距
block=128    1310.7 GB/s (84.3%)   1302.0 GB/s (83.7%)
block=256    1319.5 GB/s (84.8%)   1302.0 GB/s (83.7%)
block=512    1310.7 GB/s (84.3%)   1302.0 GB/s (83.7%)
block=1024   1310.7 GB/s (84.3%)   1310.7 GB/s (84.3%)
```

v0 在 block=32 时只有 **32.8%**，到 128 才追平。v1 **从 32 开始就是满的**，
而且从 32 到 1024 的波动只有 1.1 个点。

原因是**在途访存请求数（memory-level parallelism）**。要把 1555 GB/s 的
带宽喂满，必须同时有足够多的访存请求在飞。v0 一个线程只发 1 个 load，
block=32 时每个 SM 上能驻留的线程数受限于「每 SM 最多 32 个 block」，
线程不够 → 请求不够 → 带宽跑不满。v1 一个线程发 4 个元素的请求
（打包成一条 128 bit 指令），**同样的线程数，4 倍的在途数据量**。

> 这就是 §1 那个反直觉结论的解释：**向量化不是让带宽变快，
> 是让你用更少的线程就能把带宽喂满**。
> 在 block=256 这种「线程本来就够多」的配置下，它自然看不出收益。
> 它的价值在于让 kernel 对配置**不敏感** —— 这在真实项目里很值钱，
> 因为你不总有机会为每个 kernel 扫参数。

对比 `../../triton/01_vector_add/`：那边扫 `BLOCK_SIZE` 从 128 到 16384
**差距不到 2%**，因为 Triton 的 `BLOCK_SIZE` 是「一个 program 处理多少元素」，
不是「一个 block 开多少线程」—— 线程数由编译器根据 `num_warps` 定。
**两个参数名字像，含义完全不同**，这是从 Triton 转 CUDA 最容易混的一处。

### 3.2 向量化在指令层面发生了什么

`make ptx` / `make sass` 直接看得到：

```
=== v0_naive ===        PTX: ld.global.nc.f32        SASS: LDG.E.CONSTANT
=== v1_vec4  ===        PTX: ld.global.nc.v4.f32     SASS: LDG.E.128.CONSTANT
                        PTX: st.global.v4.f32        SASS: STG.E.128
```

`v4.f32` / `.128` 就是 128 bit 一条的访存指令。搬同样多的数据，
v1 的 load 指令数是 v0 的 1/4，地址计算也少 3/4。

**和 Triton 的关键差别**：Triton 里没有 `float4`，你**不能**直接要求向量化。
你只能保证访问模式连续，然后编译器自己决定 —— 实测它会，
`../../triton/01_vector_add/bench.py` 的 `ptx_vectorization()` 就是去 PTX 里
grep `ld.global.v4.b32` 来验证这件事的。

> 一句话：**CUDA 把方向盘给你，Triton 替你打**。
> Triton 打得不错（这个 kernel 上它自己就 vectorize 了），
> 但你没法在它打错的时候接管 —— 只能改访问模式去「暗示」它。

### 3.3 合并访存从哪一步崩？—— 答案不是 cache line

这是本练习最值得记住的一个测量。`v3` 让每个线程处理 `per_thread` 个
**连续**元素（CPU 程序员的本能写法），`per_thread` 就等于 warp 内
相邻线程的地址间距。扫一遍：

| per_thread | 地址间距 | 带宽 | 占峰值 | vs v0 |
|-----------|---------|------|-------|-------|
| 1 | 4 B | 1310.7 GB/s | 84.3% | — |
| 2 | 8 B | 1319.5 GB/s | 84.8% | — |
| 4 | 16 B | 1310.7 GB/s | 84.3% | — |
| **8** | **32 B** | 1045.8 GB/s | 67.2% | **1.26×** ← 开始掉 |
| 16 | 64 B | 558.5 GB/s | 35.9% | 2.36× |
| 32 | 128 B | 215.3 GB/s | 13.8% | **6.13×** |
| 64 | 256 B | 200.6 GB/s | 12.9% | 6.58× |
| 128 | 512 B | 312.6 GB/s | 20.1% | 4.22× |
| 512 | 2 KB | 228.1 GB/s | 14.7% | 5.79× |
| 2048 | 8 KB | 143.9 GB/s | 9.3% | **9.17×** |

**分水岭是 32 字节，不是 128 字节。** 我原本以为是 cache line（128 B），
写在注释里，被测量打脸了。真正的粒度是 **sector（32 B）** ——
NVIDIA 的 L1/L2 以 32 字节的 sector 为最小访存单位，一条 cache line
是 4 个 sector。间距一到 32 B，warp 里 32 个线程就落进 32 个不同的 sector，
一条 load 指令要碰 32 个 sector 而不是 4 个。

两个值得注意的细节：

1. **是渐变不是断崖**（67% → 36% → 14%）。因为 L1 还能吸收一部分复用：
   同一个线程的下一次循环迭代会用到同一个 sector。间距越大，
   一个 warp 的工作集越大，L1 越兜不住。
2. **间距很大之后不再单调**（128 B 的 6.13× 比 512 B 的 4.22× 还差）。
   这一段掺进了 TLB、cache set 冲突、显存 partition camping 等因素，
   我没有进一步归因 —— 只记录观察到的现象。反正都是「很慢」，
   实践上没有区分的价值。

> 实用价值：知道**「32 字节」这条线**，你在写代码的时候就能直接算出
> 会不会踩坑，不用等 profile。比记住「要合并访存」这句空话有用得多。

对照 `../../triton/01_vector_add/` 的同一个实验：那里用 cyclic 偏移
（间距 = program 数 × 4 B，非常大）测到 **5.8×** 的惩罚，
落在这张表的 512 B 那一行附近（5.79×）—— **两个框架、两套代码，
测到的是同一个硬件事实**。

### 3.4 grid-stride：开多少 block 够用？

```
grid=108  (1/SM)    1123.5 GB/s  (72.2%)
grid=216  (2/SM)    1252.3 GB/s  (80.5%)
grid=432  (4/SM)    1293.5 GB/s  (83.2%)   ← 默认值
grid=864  (8/SM)    1276.7 GB/s  (82.1%)
grid=1728 (16/SM)   1302.0 GB/s  (83.7%)
grid=3456 (32/SM)   1310.7 GB/s  (84.3%)
对照：v0 的 grid = 65536（由 n 决定）      1310.7 GB/s  (84.3%)
```

每 SM 1 个 block 明显不够（72%），4 个就基本饱和。
但注意：**grid-stride 最终也只是追平 v0，没有超过**。

这和 `../../triton/02_fused_softmax/` 里 persistent kernel 的结论一致 ——
在一个 launch 开销可以忽略、工作量均匀的 kernel 上，
「减少 block 数量」换不来任何东西，反而可能损失并行度。
grid-stride 的价值在**别的地方**：任意 n 都能跑、grid 大小可控、
`<<<1,1>>>` 就能串行调试。**别把它当性能优化用。**

### 3.5 ⚠️ 小数据量测出来的是 L2 带宽，不是显存带宽

```
n=2^12 (0.05 MB)      9.6 GB/s   (0.6%)   ← 太小，全是 launch 开销
n=2^16 (0.75 MB)    153.6 GB/s   (9.9%)
n=2^18 (3.00 MB)    512.0 GB/s  (32.9%)
n=2^20 (12.0 MB)   1536.0 GB/s  (98.8%)   ← ★ 98.8%？不可能
n=2^22 (48.0 MB)   1170.3 GB/s  (75.2%)
n=2^24 (192  MB)   1319.5 GB/s  (84.8%)
n=2^26 (768  MB)   1363.0 GB/s  (87.6%)
```

`n=2^20` 那行报出 **98.8% 的「显存带宽」**，比 `cudaMemcpy` 还高。
这不是我的 kernel 写得好，是**它根本没碰显存**：三个数组一共 12 MB，
装得进 A100 的 40 MB L2，benchmark 循环 50 次，第一次之后全是 L2 命中。

这个坑很常见 —— 拿一个小 buffer 测「带宽」，测出个漂亮数字，
换成真实规模就打回原形。

> **规则：测显存带宽，工作集必须显著大于 L2。**
> A100 的 L2 是 40 MB，所以这里用 n=2²⁴（192 MB）当主测点。
> 顺带一提，这也解释了 `../../triton/03_matmul/` 里
> GROUP_M 在 4096² 上毫无效果 —— 同一个 40 MB 在起作用。

## 4. 一句话总结

| 优化 | 收益 | 真实原因 |
|------|------|---------|
| 合并访存 | **不做的话慢 6~9 倍** | 32 B sector 是最小访存单位 |
| `float4` 向量化 | 大 block 上 **0**（±1% 噪声），**block=32 上 2.6 倍** | 提高在途请求数，不是提高带宽 |
| grid-stride | **0%** | 不是性能优化；价值在灵活性和可调试性 |
| 调 block 大小 | v0 上 2.6 倍，v1 上 **0%** | 向量化之后就不敏感了 |

**这个 kernel 的天花板是 ~85%**（`cudaMemcpy` 只有 83.4%）。
v0 已经 84.8%，没有优化空间了。想再快只有一条路：**减少访存量**
（也就是融合，见 `../../triton/02_fused_softmax/`）。

## 5. 踩坑记录

1. **反面教材一开始「不反」**。`v3` 第一版 `per_thread` 写死 4，
   测出来和 v0 一样快（84.3% vs 84.8%）。因为间距只有 16 B，
   一个 warp 覆盖的 512 字节仍然是连续的，DRAM 侧搬的字节数没变。
   → 想演示一个负面效应，得先确认**你真的触发了它**。
     测出「没差别」时，第一反应应该是「我的实验设计错了」，
     而不是「这个优化没用」。改成扫参数之后才看到完整的 §3.3 那张表。

2. **我预测的阈值是错的**。注释里写「cache line 128 字节是分水岭」，
   实测是 **32 字节的 sector**。写进注释的数字，测之前都只是猜测。

3. **小 buffer 测出 98.8% 的带宽** —— §3.5。比峰值还高就该警觉了。

4. **`make sass` 一开始报 `cuobjdump: not found`**。
   `nvcc` 能用不代表 `cuobjdump` / `ncu` / `nsys` 在 PATH 里 ——
   它们都在 `/usr/local/cuda/bin/` 下但默认没加进去。
   `common.mk` 里现在一律用全路径，Makefile 开箱即用。

5. **正确性用例必须包含非整除尺寸**。`CASES` 里放了 1000、98765、
   `2^20 + 3` —— 特别是最后那个，专门测 `float4` 的尾巴处理
   （n 不是 4 的倍数）。整除的尺寸全是假的绿灯。

6. **`cudaMemset(dout, 0xFF, ...)` 再跑 kernel**。不先污染输出缓冲区的话，
   「kernel 根本没启动」和「kernel 算对了」在结果上可能看不出区别
   （比如 grid 算成 0）。

7. **`compute-sanitizer` 下性能数字全废**（4229 GB/s → 47.6 GB/s，慢 ~30 倍）。
   它是查正确性的，不是查性能的，两件事别混在一次运行里。
   `make sanitize` 因此用 `--quick`。

8. **`bench()` 的 warmup 热不了 GPU 时钟。** 每次测量前空跑 10 遍只够热
   module 载入和 cache，拉不动时钟 —— 进程里第一个被测的变体会虚慢
   20~30%。现在 `main()` 里先调 `warmup_gpu()`（`../common.cuh`）空转
   200 ms。这个坑在 `../02_reduction` 里害我写错过一整张表，
   详见那边的 README §5.6。

   收益和向量宽度是线性关系吗？

   再用 `make sanitize` 看。错误信息长什么样？结果一定会错吗？

## 7. 和 Triton 版的对照

| | CUDA（本目录） | Triton（`../../triton/01_vector_add/`） |
|---|---|---|
| 并行粒度 | 手写到单个 thread | 一个 program 处理一整个向量 |
| 边界处理 | `if (i < n)` 自己写 | `mask=` 参数 |
| 向量化 | `float4` 显式控制 | 不可控，编译器自动（实测会做） |
| block 大小 | 影响 2.6 倍（v0） | 影响 < 2% |
| 合并访存惩罚 | 6~9 倍 | 5.8 倍（同一个硬件事实） |
| 代码行数 | ~50 行 × 4 文件 | ~30 行 × 4 文件 |

**共同结论**：这个 kernel 在两个框架下都能打到 ~85% 的带宽上限，
差别只在你要写多少、能控多少。Triton 的抽象在这里几乎没有代价 ——
真正需要 CUDA 的是下一个练习（`../02_reduction/`，要用 shared memory
和 warp 原语）和 `../03_matmul/`（要手写 tiling）。
