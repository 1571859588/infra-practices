# 04 relu —— 分支、in-place、融合

`out = max(x, 0)`，float32。比 01 的 vector_add 还简单：1 个比较、
0 次乘加，读 x 一遍写 out 一遍，**8 字节/元素**。
算术强度是 0 —— 性能就是带宽，一点悬念都没有。

所以这个练习的目的**不是**把 relu 写快（写不快了，01 已经证明
最朴素的流式 kernel 就贴着 ~85% 的天花板），而是回答三个
只在 ReLU 这种「简单到没有优化空间」的算子上才看得清楚的问题：

1. **手写 if/else 会有 warp divergence 吗？** 输入一半正一半负，
   「该分裂的时候分裂」——直觉上该慢一倍。实测：一点也不慢。
2. **in-place 能省带宽吗？** 流量一分不省（读一遍写一遍照旧），
   省的是**显存占用** —— L2 的临界规模翻倍。
3. **那 ReLU 的优化空间在哪？** 在**别的 kernel 的 epilogue 里**：
   融合能让 ReLU 的 8 B/elem 访存整个不发生（实测 1.70x）。

和 `../01_vector_add/` 的关系：结构（合并访存 / float4 / grid-stride）
那边已经讲透了，这里只复用不重复；本练习的增量是上面三个问题。

测试环境：A100-SXM4-40GB（108 SM，40 MB L2，峰值带宽 **1555.2 GB/s**），
CUDA 12.4，`-arch=sm_80`。实测用空闲卡（邻居只占显存、0% util，
不影响带宽测量）：主体数据在 GPU 4，v2b 归因实验在 GPU 0 补测 ——
两张卡上 memcpy / v0 / v1 的数字**逐 µs 一致**，v2 差 1%，可跨卡比较。

## 1. 变体一览

| 文件 | 做了什么 | 实测（n=2²⁴） | 占峰值 |
|------|---------|--------------|-------|
| `v0_naive.cu` | 一线程一元素，三元运算符 | 1285.0 GB/s | 82.6% |
| `v0_naive.cu`（ifbranch） | 同上，源码写成 if/else | 1285.0 GB/s | 82.6% |
| `v1_vec4.cu` | `float4` 向量化 | **1310.7 GB/s** | **84.3%** |
| `v2_vec4_grid.cu`（v2b） | 纯标量 grid-stride | 1225.0 GB/s | 78.8% |
| `v2_vec4_grid.cu` | float4 + grid-stride | 1225.0 GB/s | 78.8% |

参考点：`cudaMemcpy` D2D 是 1310.7 GB/s（84.3%）—— 注意这个参考点
比 01 里的更有说服力：**memcpy 读一遍写一遍（8 B/elem），和 ReLU 的
理想访存量一模一样**，还一个数都不算。它就是 ReLU 的物理天花板。

三个观察：

- **v1 追平 memcpy**（1310.7 = 1310.7），v0 差 2 个点。
  和 01 §3.1 的 MLP 结论一致：这个 kernel 每线程只有 1 个 4 B load，
  在途请求数比 01 的 v0（每线程 2 个 load）还少，所以 scalar 版
  更容易喂不满。
- **三元版和 if/else 版一模一样快**（104.4 µs = 104.4 µs，
  两次独立 run 都是）。原因见 §3.1 —— 分支根本不存在。
- **v2b（标量）和 v2（float4）在默认 4/SM 下掉得一样多**（都是
  109.6 µs，比各自的非循环版慢 4~6 个点）—— 损失来自**循环本身**，
  不是 float4 和循环的组合。但把 grid 开到 32/SM 能基本追平，
  1/SM 时 float4 反而救命。完整归因见 §3.2。

## 3. 实测结果

### 3.1 手写 if/else 一样快 —— 因为分支根本不存在

先猜：warp 是 32 个线程锁步执行的，输入一半正一半负时，
一半线程走 if、一半走 else，**该分裂的时候分裂** ——
直觉上至少慢 1.5 倍。实测四种符号分布（n=2²⁴，v0）：

```
全正          104.4 us    1285.0 GB/s  (82.6%)
全负          104.4 us    1285.0 GB/s  (82.6%)
正负各半      104.4 us    1285.0 GB/s  (82.6%)   ← 该分裂的时候，没慢
90% 负        104.4 us    1285.0 GB/s  (82.6%)
```

连趋势都没有。`make sass` 看 `v0_naive.cubin` 里两个 kernel 的真身：

```
relu_naive（三元）:           relu_ifbranch（if/else）:
  LDG.E.CONSTANT R2            LDG.E.CONSTANT R3
  FMNMX R7, RZ, R2, !PT        FSETP.GT.AND P0, R3, RZ
  STG.E [R4], R7                 @!P0 STG.E [R4], RZ   ← 谓词化：负数写 0
  BRA                          STG.E [R4], R3           ← 正数写 x
                               BRA
```

两种写法都没有 `BRA` 式的分支分裂，但走的路子不同：

- **三元 → 一条 `FMNMX`**（max/select），一次搞定；
- **if/else → 谓词化（predication）**：编译器没把它变成 FMNMX，
  而是生成**两条都存在、由谓词开关的 store** —— 每个线程执行两条 STG，
  但各自只有谓词为真的那条真正写入。指令多了，分支还是没有。

> 教科书上的 "warp divergence" 说的是 `BRA` 层面的控制流分裂。
  对**短的** if/else，编译器会优先用 FMNMX 或谓词化把分支消掉 ——
  真正付 divergence 代价的是**分支体很长**或**控制流复杂**的代码。
  "ReLU 一半正一半负会很慢" 这个直觉，在 SASS 层面就没有立足点。

顺带的教训：**我预测的机制是错的**（以为 if/else 也会编成 FMNMX），
但预测的结论碰巧对（一样快）。结论对不代表解释对 ——
不看 SASS，这个解释就写错了。

### 3.2 grid-stride 那 6 个点去哪了：循环本身，不是组合

表里 v2（float4+grid-stride）比 v1（float4）慢 6 个点。两种解释：
(a) 循环本身有代价；(b) float4 和循环**组合**才出问题。
拆开的办法：加一个 v2b —— **纯标量**的 grid-stride，循环体和 v0
一模一样。默认配置（4/SM）下的四方对照：

```
  v0（标量，无循环）     104.4 us   1285.0 GB/s  (82.6%)
  v2b（标量 + 循环）     109.6 us   1225.0 GB/s  (78.8%)   ← 循环让标量掉 3.8 个点
  v1（float4，无循环）   102.4 us   1310.7 GB/s  (84.3%)
  v2（float4 + 循环）    109.6 us   1225.0 GB/s  (78.8%)   ← 循环让 float4 掉 5.5 个点
```

**归因清楚：是 (a)**。标量版套上循环掉得一样多，float4 没有额外背锅。
但「循环有代价」这个说法太粗 —— 扫一下 grid 大小，真正的机制浮出来：

```
                     v2b（标量）             v2（float4）
grid=108  (1/SM)     956.7 GB/s  (61.5%)   1260.3 GB/s  (81.0%)   ← 差 20 个点！
grid=216  (2/SM)    1129.9 GB/s  (72.7%)   1236.5 GB/s  (79.5%)
grid=432  (4/SM)    1225.0 GB/s  (78.8%)   1225.0 GB/s  (78.8%)   ← 默认值，打平
grid=864  (8/SM)    1180.8 GB/s  (75.9%)   1225.0 GB/s  (78.8%)
grid=3456 (32/SM)   1272.5 GB/s  (81.8%)   1297.7 GB/s  (83.4%)   ← 都追平 v0/v1
```

三个观察：

1. **4/SM 时掉、32/SM 时不掉** —— 说明不是「循环开销」这种固定成本，
   而是**在途请求数（MLP）不足**：432 block × 256 线程 = 11 万线程，
   每线程 38 轮，一轮的 store 发出去到下一轮的 load 之间有一个
   DRAM 延迟（~800 ns）的气泡，驻留 warp 不够多就盖不住。
   32/SM 时驻留 warp 翻几倍，气泡被并行度淹没。
2. **1/SM 时 float4 反而救命**（61.5% → 81.0%，+19.5 个点）——
   01 §3.4 的结论在 ReLU 上原样复现：线程太少时，向量化是把
   在途字节拉回来的唯一办法。01 里这个差距是 71.8→82.6。
3. **和 01 对照出第三个事实**：那边 12 B/elem，v4@4/SM 只掉 2 个点
   （81.6 vs 83.7）；这边 8 B/elem 掉 5.5 个点。每轮在途字节越少，
   迭代间的气泡越伤 —— **同一个 grid-stride 结构，在不同访存量的
   kernel 上税不一样**。

> 实用结论：`common.mk` 里「每 SM 4 个 block」这个默认经验值
> 不是免费的。对 12 B/elem 的 vector_add 它只收 2 个点的税，
> 对 8 B/elem 的 ReLU 收 5.5 个。轻 kernel 上要么把 grid 开到
> 32/SM，要么别用 grid-stride —— 01 那句「grid-stride 不是性能优化」
> 在这里要加半句：**默认配置下它还倒贴**。

### 3.3 in-place：省的是占用，不是流量

in-place（`x = relu(x)`，x 和 out 是同一个 buffer）不省任何流量：
照样读一遍写一遍，8 B/elem 一分不少。它省的是**显存占用** ——
工作集从 2n 缩到 n。用 v1 扫规模（流量口径两种完全相同）：

```
                out-of-place            in-place
n=2^18           409.6 GB/s  (26.3%)     341.3 GB/s  (21.9%)  ← 太小，launch 开销主导
n=2^20          1024.0 GB/s  (65.8%)    1024.0 GB/s  (65.8%)
n=2^22 (16 MB)  1310.7 GB/s  (84.3%)   **2340.6 GB/s (150.5%)** ← in-place 工作集 16 MB < L2
n=2^23 (32 MB)  1213.6 GB/s  (78.0%)    1260.3 GB/s  (81.0%)   ← in-place 32 MB 勉强进 L2
n=2^24 (64 MB)  1310.7 GB/s  (84.3%)    1285.0 GB/s  (82.6%)  ← 都出 L2 了，没差别
n=2^25         1351.3 GB/s  (86.9%)    1330.7 GB/s  (85.6%)
```

三个值得读的行：

1. **n=2²² 的 in-place 报了 150.5%** —— 超过 DRAM 峰值，因为这个
   规模下工作集（16 MB）整个住进了 40 MB L2，读写全走 L2，
   2340 GB/s 是 **L2 的带宽**，不是显存的。和 01 §3.5 的
   "98.8% 是假带宽" 是同一个现象的另一面：那边是 out-of-place
   恰好装进 L2，这边是 in-place 把临界规模**翻倍**后恰好装进。
2. **in-place 的收益是阶跃的，不是渐变的**：要么整个工作集进 L2
   （n=2²²，+79%），要么进不去（n≥2²⁴，±2% 噪声）。
   "in-place 快不快" 不是一个好问题，"工作集有没有因此掉进 L2" 才是。
3. **n=2²³ 的 out-of-place（78.0%）比 n=2²⁴ 的（84.3%）还慢** ——
   工作集 64 MB 刚好骑在 40 MB L2 上，部分命中 + 写回驱逐的
   交互比"干脆全不命中"更糟。这个行在两张卡上测出过 78% 和 98%
   两个值（邻居的 L2 残留决定你的命中率），是整个 benchmark 里
   最不稳的一行，别把它当结论，但要知道有这个现象。

> 实用价值：训练代码里激活内存减半 = L2 临界规模翻倍，
  中小张量上这是白捡的加速；大张量上省的是显存本身（能不 OOM）。
  另外 ReLU 是**幂等**的（relu(relu(x)) == relu(x)），in-place 反复跑
  数据不坏 —— 换个非幂等算子（比如 x = x*2+1），第二次迭代起
  你测的就是别的函数了。

### 3.4 融合：ReLU 唯一有意义的优化

`out = relu(x + y)`，两种写法（n=2²⁴）：

```
两个 kernel（add → relu）   261.1 us    1285.0 GB/s  (82.6%)  ← 20 B/elem
融合 kernel（add + relu）   153.6 us    1310.7 GB/s  (84.3%)  ← 12 B/elem
```

墙钟 **1.70x**。注意两行报出的带宽几乎一样 —— 都在 ~84% 的
天花板上，谁也没跑得更快。**快出来的 1.70x 全部来自少搬数据**：

```
两个 kernel：读x 读y 写tmp (12) + 读tmp 写out (8) = 20 B/elem
融合      ：读x 读y 写out                     = 12 B/elem
理论加速比 20/12 = 1.67x，实测 1.70x
```

中间结果 tmp 在融合版里只存在于**寄存器**里（`FMNMX` 直接消费
`FADD` 的输出），显存往返整个消失。

> 这就是为什么单独 benchmark ReLU 是个**没有意义的问题**：
> 它自己已经 84% 了，优化链上一行都省不出来；但它作为
> **别人的 epilogue**，能把 8 B/elem 的整个 kernel 变成
> 前一个 kernel 里的一条 FMNMX。PyTorch 里 `x + y` 然后
> `F.relu(x)` 的两行代码，和 torch.compile / Triton 融合后的
> 差别就是这个 1.70x。
>
> Triton 对照：`../../triton/03_matmul/v3_fused_relu.py` ——
> 同一件事在 Triton 里是往 matmul kernel 里加一行 `tl.maximum`；
> 融合思想的完整版（4.3x 那个）在 `../../triton/02_fused_softmax/`。

## 4. 一句话总结

| 优化 | 收益 | 真实原因 |
|------|------|---------|
| 手写 if/else 分支 | **0**（= 三元） | 编译器用 FMNMX / 谓词化把分支消了 |
| `float4` 向量化 | +2 个点（82.6→84.3） | 和 01 一样：补在途请求数 |
| grid-stride（默认 4/SM） | **-4~-6 个点**（标量/float4 同罪） | 循环迭代间的延迟气泡：MLP 断流（§3.2） |
| grid-stride（32/SM） | -1 个点，基本追平 | 驻留 warp 多了，气泡被盖住 |
| grid-stride（1/SM） | 标量 61.5%；float4 **+19.5 点** | 向量化是低占用下唯一的救命稻草 |
| in-place | 大张量 0；工作集因此进 L2 时阶跃 +79% | 省占用不省流量，收益看 L2 临界规模 |
| **融合进 epilogue** | **1.70x** | 8 B/elem 的访存整个消失，比任何 kernel 内优化都大 |

**单独的 ReLU 没有优化空间**（v1 = memcpy = 天花板）。
它的全部价值在于让别人融合 —— 这也是「elementwise 算子
该不该有自己的 kernel」这个工程问题的标准答案。

## 5. 踩坑记录

1. **融合对比的带宽第一次报出了 5242 GB/s（337% 峰值）**。
   原因：`bytes` 把「12 B/elem」又乘了一个 `sizeof(float)` ——
   每元素字节数里已经含着那个 4 了。报出**超过物理上限**的数字，
   第一反应应该是"我算错了"而不是"我写出了宇宙第一 kernel"。

2. **同一张卡三次 run，memcpy 从 84.3% 漂到 93.6%**。
   GPU 0 的邻居进程在间歇性计算，每次 run 污染 L2 的程度不同。
   换到完全空闲的 GPU 4 之后，数字和 01 的记录严丝合缝
   （memcpy 1310.7 / 84.3%，两次独立 run 一致）。
   **数字漂了先查卡，再怀疑代码。**

3. **工作集 ≈ L2 的那几行是全表最不稳的**。n=2²³ 的 out-of-place
   在两张卡上测出过 78% 和 98% —— 骑在 L2 临界点上的数字
   由邻居的 L2 残留决定。要复现本表请用空卡。

4. **预测的机制错了一半**。§3.1 我以为 if/else 也会编成 FMNMX，
   实际是谓词化双 store。结论（一样快）碰巧对，解释差点写错 ——
   结论对不代表机制对，SASS 才是判决书。

5. **v0 和 v1 差 2 个点，01 里只差 1 个点**。不是玄学：这个 kernel
   每线程只有 1 个 load（01 的 v0 有 2 个），在途请求数更少，
   scalar 版更容易喂不满带宽。同一个结构在不同访存量的 kernel 上
   表现会移动，结论别跨 kernel 生搬硬套。

6. **看卡不能只看 util，还要看剩余显存**。GPU 4 上一分钟前还能跑
   full run，一分钟后邻居把显存从 39.2 GB 吃到 40.2 GB（共 40 GB），
   连正确性检查的 4 MB 都分配不出来，直接 OOM 退出。
   `nvidia-smi` 的 `memory.used` 逼近上限时，换卡再跑。

## 7. 和 Triton 版的对照

`../triton/` 没有单独的 relu 练习 —— 正是因为 Triton 的答案只有
一个（融合），没有「怎么写好一个独立 relu kernel」的中间地带：

| | CUDA（本目录） | Triton |
|---|---|---|
| 独立 relu kernel | 本练习：v0/v1/v2，84% 天花板 | 不值得写，`torch.relu` 就是 |
| 分支怎么处理 | 显式（三元/FMNMX、if/else/谓词化） | `tl.maximum`，编译器管 |
| in-place | 自己保证（幂等性、别名） | `tl.store` 到原指针，同样自己保证 |
| **融合** | **epilogue 手写**（§3.3 的 1.70x） | **加一行 `tl.maximum`**（`triton/03_matmul/v3_fused_relu.py`） |

**共同结论**：elementwise 算子的性能故事全部在融合里，
不在 kernel 写法里。两边测到的是同一个事实 ——
CUDA 侧把它拆开给你看，Triton 侧直接给你结论。
