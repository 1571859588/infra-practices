问题一：在途请求数（MLP）

先接受一个反差：显存非常慢

GPU 做一次 max(x, 0) 大约只要 1 纳秒；但从显存把 x 取回来，一个来回要 ≈ 700 ns。 比例大概是：砌一块砖 1 秒，去仓库搬这块砖要 12 分钟。如果每次都「搬一块 → 砌一块 → 再去搬下一块」， 砌砖的手 99% 的时间都在闲着。

带宽是「吞吐」，不是「单程速度」

1555.2 GB/s 的意思不是「数据 700 ns 能到」，而是「这条总线**每个时刻**都在过这么多货」。 就像高速公路：车道吞吐量 × 单程耗时 = 必须常驻在路上的货车总量。 想跑满带宽，路上必须一直有足够多的货 —— 这就是「在途请求数」。

开始算账：ReLU 每个线程能贡献多少「在途」

看 v0_naive.cu 的循环体：每个线程读 1 个 float（4 B）、写 1 个 float（4 B）， 所以满打满算一个线程身上同时在飞的只有 8 B。要凑够 1.1 MB：

需要 ≈ 1.1 MB ÷ 8 B ≈ 14 万个线程同时在等
A100：108 个 SM × 每 SM 最多驻留 2048 线程 = 22 万线程容量 → 勉强够 → 实测 v0 = 82.6%

三个会「饿死」总线的因素，正好对应三次实测翻车：

① 驻留的线程不够多。grid 开小了，或者 block 太小把「车位」浪费了 —— 每 SM 有 64 个 warp 车位， 但最多只驻留 32 个 block：block=32（一个 block 才 1 个 warp）时车位只用一半，只有 11 万线程上线。

② 每个线程发的字节太少。这是 float4 的出场时机：同样的线程数， 一次发 128 bit（16 B）而不是 32 bit（4 B），每线程在途 8 B → 32 B，直接 ×4。 grid=108（8 个 warp）时标量版在途只有约 0.2 MB，float4 版约 0.86 MB —— 接近 1.1 MB 的需求， 所以 61.5% 被拉到 81.0%。线程不够，就拿字节凑。

③ 循环把「在途」掐成了一段一段。grid-stride 版每线程要循环 38 轮， 一轮的读写发完、还没回来之前，这个线程就干等。车位只停一半时（4/SM，32 个 warp）， 别的 warp 不够多、盖不住这个间隙，于是「量够了但断了流」—— 这就是 README §3.2 里 v2b 和 v2 在 4/SM 都掉到 78.8% 的原因：掉的点数一样，说明是循环本身在漏气， 跟 float4 没关系。

量级估算：满发在途 = 驻留线程 × 每线程字节；未计发射率与循环断流，所以它解释「够不够」的方向，不是精确预测。实测参考（grid-stride 版）：1/SM → 61.5% / 81.0%，4/SM → 78.8% / 78.8%，32/SM → 81.8% / 83.4%。

一句话。带宽是吞吐，延迟要靠「同时在飞」的量去填。这个量 = 驻留线程数 × 每线程发的字节数。 grid 太小、block 太小、不用向量化、循环断流 —— 四种做法饿死总线的方式不同，账是同一本。

问题二：in-place 与 out-of-place

代码在哪：就是换了一个指针

它不是两个 kernel。v1_vec4.cu 里只有一个 relu kernel， 它只做「读 x[i] → 取 max → 写 out[i]」，根本不知道自己是不是 in-place。 区别全部发生在 bench.cu 的 sweep_inplace_size() 里，调用时传的指针不同：

//                输入指针   输出指针
launch_v1_vec4(buf.dx, buf.dout, n, 0);  // out-of-place：x 和 out 是两块显存
launch_v1_vec4(buf.dx, buf.dx,   n, 0);  // in-place：    同一块，读它也写它
//                    ↑ 同一块显存，既是输入又是输出

流量一分没省

直觉容易以为 in-place「只写不读」所以快一半 —— 不是。该读的一遍还是要读， 该写的一遍还是要写，两种调法都是 8 B/元素，总线上的车流一模一样。 那 in-place 到底省了什么？省的是占地面积 —— 而占地面积之所以值钱，是因为 L2。

显存旁边有个 40 MB 的小仓库

现在把两个事实拼起来：in-place 把工作集从 2n 缩到 n，L2 只有 40 MB —— 于是存在一个分水岭规模，out-of-place 还没挤进去、in-place 已经整个住下了。 在 n=2²²（数组 16 MB）正好跨线：

条形越过 DRAM 峰值竖线只有一种解释：那些读写根本没走显存，走的是更快的 L2。

读这张表的三个要点：

① n=2²² 是唯一的分水岭：in-place 工作集 16 MB 舒服地住进 L2，带宽 2340.6 GB/s （150.5%，分母是 DRAM 峰值，实际测到的是 L2 带宽），比 out-of-place 快 79%。 out-of-place 的 32 MB 名义上也「装得进」40 MB，但挤着住、被写回和驱逐搅和，只拿到 84.3%。

② 两边都不沾 L2 时（n≥2²⁴），完全没差别：±2% 就是噪声。流量相同、层次相同，凭什么有差别。

③ n=2²⁰ 两边都只有 65.8%：工作集 8 MB 明明全进 L2，为什么不满？ 因为总量太小 —— 总耗时只有 8 µs，kernel 启动的固定开销（约 5 µs）占了大头。 小张量上先看启动开销，再看带宽。

最后一块拼图：为什么 in-place 敢反复跑

benchmark 会把同一个调用跑几十遍。in-place 意味着第 2 遍的输入是第 1 遍的输出 —— 数据被自己改了。ReLU 敢这么干是因为幂等：

relu(relu(x)) = relu(x)
已经 ≥ 0 的数再过一遍 ReLU 不变 → 跑一百遍，测的都是同一个函数
换成非幂等算子就是 bug。比如 x = x * 2 + 1：第 2 遍测的是 2x+1 的 2x+1…… benchmark 从第 2 次迭代起测的根本不是你要测的函数。这类 in-place 基准必须每轮重新上传数据。 （另外注意编译器层面 in-place 还要求「读写不别名、线程不互踩」—— 本 kernel 每线程只碰自己的元素，安全。）
一句话。in-place 省的是占地面积，不是流量。占地减半 → L2 的临界规模翻倍 → 工作集跨线的那一档，白捡一大截「假带宽」（其实是 L2 带宽）；没跨线的规模，一分钱不省。 训练代码里它真正的日常收益是：激活显存减半，不容易 OOM。
